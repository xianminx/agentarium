# 02 — 5 个产品方案：PRD / MVP 对比

每个方案给出：定位、MVP 范围、数据模型要点、8 周能否做出、致命风险。

---

## 方案 A — GTM Agentic Table（"更好的 Clay"）

**定位**：面向 B2B 销售团队的公司研究 + ICP 打分 + 个性化外联表。

**MVP**：导入公司列表 → AI Research 列 → ICP Score 列 → 信号监测 → 生成邮件 → 推 CRM。

**8 周可行性**：✅ 最容易，因为路径全是已知的。

**致命风险**：
- Clay $150M ARR / $5B 估值，且 2026 年把 Workflows **永久免费**送给所有付费档。
- 赛道还挤着 Unify、Attio、Gumloop、Keyplay、Common Room。
- 客户换 Clay 的成本是"重建全部 play + 重新买数据商"，切换意愿极低。

**判断**：❌ 不做。这是唯一一个在位者**主动在降价**的赛道。

---

## 方案 B — 通用 Agentic Table（"Airtable for agents"）

**定位**：水平通用，任何一组 records 都能挂 agent 列与 workflow。

**MVP**：多数据源导入 + 自定义表 + agent 列 + workflow + 审批 + 动作连接器。

**8 周可行性**：❌ 做不完。水平通用意味着你要同时做 Airtable 的编辑器、
Zapier 的连接器矩阵和 Clay 的 enrichment 网络。

**致命风险**：
- 水平产品没有"第一个非要用不可的理由"，获客成本极高。
- Airtable 已经 AI-native 重启，分销远强于你。
- 通用 = 每个用户的 agent 都要自己调，没人会调，留存崩。

**判断**：⚠️ 这是**愿景**，不是**第一个产品**。作为架构约束保留（不要写死任何 GTM 字段），但不要作为 MVP。

---

## 方案 C — Agent Data Runtime（headless，MCP + SDK 优先）

**定位**：给外部 agent（Claude / Cursor / 自建）一个带 schema、稳定行标识、版本化的结构化数据后端。

**MVP**：REST + MCP server + 稳定 row id + 列语义元数据 + 持久指令 + 快照导出 + 极简 Web 表格。

**8 周可行性**：✅ 可行（工程量最小）。

**致命风险**：
- **Rowset 已经在做，且几乎逐项命中**（稳定 header、语义列元数据、持久 agent instructions、
  显式 index 列、MCP + REST、Qdrant 混合检索、公开预览）。
- 开发者工具 ACV 极低，变现周期长。
- 更根本的问题：如果 agent 在别处跑，你就**看不到 correction 信号**，护城河飞轮起不来。

**判断**：⚠️ 作为**接口层**必做，作为**产品定位**不做。

---

## 方案 D — Verified Research Table（垂直楔子 + 可验证列）★ 推荐

**定位**：一张会自己研究、并且**知道自己有多准**的表。
第一个垂直：**招聘 / 人才 sourcing**（理由见 03-gtm-strategy.md）。

**核心差异化**：agent column 是一个**有版本、有准确率、能弃权**的对象。

**MVP（8 周）**：

1. 导入一组实体（CSV / LinkedIn 搜索 / ATS 导出）
2. 自然语言创建 **Agent Column**：
   "判断这个人是否有 B2B SaaS 的从 0 到 1 的经验"
   → 系统自动生成：输出 schema（枚举/数值/布尔）、研究计划、弃权阈值
3. 逐行执行，每个 cell 写入：`value` + `confidence` + `evidence[]` + `run_id` + `cost`
4. **Review 模式**：连续审阅低置信度 cell，✓ 确认 / ✎ 修正 / ✕ 驳回
5. 每次修正 → 写入该列的 **golden set**
6. 列头常驻显示：`准确率 87% (n=214) · 改写率 6% · $0.021/行`
7. 改 prompt → 生成 v(n+1) → **在 golden set 上回放** → 跑赢才允许 promote
8. 一个动作出口（生成外联草稿 / 写回 ATS / Slack）

**明确不做**：多数据源同步、公式引擎、视图系统、权限矩阵、连接器矩阵。

**致命风险**：
- 冷启动：没有 golden set 时准确率显示为空，第一屏价值打折 → 缓解：内置"种子评测集"，
  首次运行强制审阅 20 行，10 分钟内产出第一个准确率数字。
- Hebbia 向下打。→ 缓解：它的交付与定价结构决定了它三年内不会做 $200/月的产品。

**判断**：✅ **推荐**。唯一一个"在位者结构性做不到"的方案。

---

## 方案 E — Trust Layer（不拥有表格，只拥有可信度）

**定位**：叠在别人的表上。接 Airtable / Google Sheets / Clay / Attio / Notion，
为已有的 AI 列提供评测、纠错闭环与准确率报告。

**MVP**：Airtable + Sheets 双连接器 + review 队列 + golden set + 准确率看板 + 回放。

**8 周可行性**：✅ 可行且最快见价值。

**优点**：
- 零迁移成本，客户不用换系统 —— 这是 2026 年最强的进入角度。
- 天然分销：Airtable marketplace、Clay 的集成生态。
- 直接吃 Salesforce 教给市场的那一课（"你的 AI 字段到底准不准？"）。

**缺点**：
- 你不拥有执行，只能观测 → 天花板低，而且**随时可能被平台原生化**。
- 客单价低，容易被当成工具而非系统。

**判断**：⚠️ 极佳的 **wedge / 试水**，糟糕的终局。可作为方案 D 的 **0 号阶段**（4 周验证需求）。

## 推荐路线：E → D，B 作为愿景，C 作为接口

```
第 0 阶段（4 周）      方案 E 的极简版，只为验证需求
  接 Airtable / Sheets 里已有的 AI 列
  问一个问题："你知道这一列有多准吗？"
  拿到 10 个客户的真实 correction 数据
        ↓  验证通过
第 1 阶段（8 周）      方案 D，招聘垂直，完整自有表格
  Agent Column + Evidence + Review + Golden Set + Version
        ↓  单垂直 PMF
第 2 阶段              开放 C 的 MCP / REST 接口
  让外部 agent 也能写入，但 eval 闭环留在自己手里
        ↓
第 3 阶段              横向复制到 procurement / 合规 / 竞争情报
  底层从第一天就不含任何垂直专有字段 → 复制成本 = 模板 + 连接器
        ↓
终局                   方案 B 的愿景，但护城河是每个客户的 golden set
```

**关键架构约束（第一天就要守住）**：
底层 entity store、agent runtime、eval 引擎中**不得出现任何招聘专有概念**。
"候选人"只是一种 entity type，"简历匹配度"只是一个 agent column 模板。
垂直化只允许存在于模板层与连接器层。
